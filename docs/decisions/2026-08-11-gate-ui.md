# Gate UI, 2026-08-11

Rationale for a set of changes to the connected-gate screen. It lives here rather than
inline because `tests/size.test.mjs` caps the eager module graph at 520 KiB and the graph
had 343 B of headroom, so prose in `app.js`, `link.js` or `session.js` is prose that costs
a user bytes on the one path the gate cannot make lazy. The comment on that ceiling says a
raise needs a reason of its own and that "made room for a feature" is not one. It still is
not one when the feature is a comment.

Everything below was measured in a real two-peer gate over a live data channel, not in a
forced screen. The before numbers come from the audit in the scratchpad run of that date.

## 1. Three surfaces reported three connection states at once

Photographed in a real gate: the header pill said `NEGOTIATING` with a live countdown, the
route badge said `RECONNECTING`, and the footer dock said "The other device never answered
the connection offer." One moment, three claims, none of them agreeing.

Three writers, no shared state:

| surface | element | writer | reads |
| --- | --- | --- | --- |
| header pill | `#status-badge` | `badge()`, on the `state` event | `Session.state`, a real aggregate |
| route badge | `#route-badge` | the `holding` and `route` handlers | nothing, a pure edge latch |
| footer dock | `#log-latest` | `log()` | nothing, append-only |

Four defects behind it, fixed as follows.

**A. A successful ICE restart never re-sampled the route.** `link.js` sets `STATE.CONNECTED`
from the `connection-state` listener when a restart succeeds, and `reportRoute()` had
exactly one call site: the key-confirmation path, which a restart skips by design because
the keys and the data channel survive it. So `#route-badge` kept whatever the drop had left
on it and a gate that recovered on the wire went on claiming it was reconnecting for the
rest of its life. `reportRoute()` is now called from that transition too. Re-sampling rather
than resetting, because a restart can move a gate from a direct pair to a relayed one and a
cosmetic reset would keep asserting the pre-drop answer.

**B. The route badge was being used as a second status display.** The `holding` handler
overwrote it with the word `RECONNECTING`, in a different vocabulary from the pill's own,
which is how two surfaces ended up disagreeing in public. The badge answers one question:
how the bytes are travelling. That answer goes stale on a drop without becoming wrong, so
it now keeps its text and gains `.is-stale`, which dims it. Opacity only, so it composites
and needs no `prefers-reduced-motion` branch.

**C. `#conn-hint` had two owners.** The `holding` handler wrote a connection state into it
and `renderDiagnostics()` wrote a routing summary into it, and the two took turns clobbering
each other for the life of the gate. The `holding` write is gone; the field describes
routing, which is what its own drawer is called.

**D. The dock never retired a warning.** `clearLog()` has one call site, the `severed`
handler, so the newest line stayed whatever the last failure wrote. The log body is
deliberately still not cleared on recovery: it is the diagnostic history of the drop that
was just survived. Instead a second `CONNECTED` now logs "Connected again.", which is a
true event and supersedes the stale line in the dock by being newer.

**E. A second gate in the same tab inherited the first one's badge.** `wire()` resets
`everConnected`, `diag` and the games session per gate and did not reset `#route-badge`,
which is written by the `route` event and by nothing else. It does now.

## 2. The desktop layout did not use its second column

Measured with three messages and two completed file rows:

| | 1920x1080 | 1440x900 |
| --- | --- | --- |
| rail height | 834 | 874 |
| `.sas-box` | 70..163 | 70..197 |
| `#sever` | 855..904 | 895..944 |
| void between them | 692 (83.0% of the rail) | 698 (79.9%) |
| `#sever` vs the fold | at the fold | 77px below it, invisible at rest |

`#games-disc` had no grid placement at all above 1024px. The declared
`grid-template-rows` had four tracks and the computed value had five: it was auto-placing
into an implicit row. Both disclosures therefore rendered in the transcript column as
1250x70 slabs carrying one short phrase each, roughly 1030px of the width empty, directly
beside a rail that was 83% empty.

The fix, chosen by the owner from three options: **both disclosures move into the rail,
above 1024px only.** They are reparented in `app.html` into `.conn-rail`, which is
`display: contents` below 1024px, so the phone and tablet reading order is byte-for-byte
what it was (route line, code, transcript, composer, connection details, games, burn) and
only the wide layout changes. This reverses the placement chosen in task #26 at desktop
widths and nowhere else.

Burn keeps `margin-top: auto` and stays at the foot of the rail. It is destructive and
irreversible and must not sit on the same rhythm as a routine control. What changed is that
the space above it now contains the two things you consult rather than read, instead of
being 692px of nothing.

One change came with it and was then taken back out the same day, which is worth writing
down because the audit was right about the symptom and wrong about the fix. The transcript
row was moved from `minmax(0, 1fr)` to `minmax(0, auto)` with `align-content: start`,
because `1fr` absorbed every spare pixel of a window that is always taller than a short
conversation: at 1920x1080 with two file rows and nothing else, the last row ended at y=375
and the box ended at y=531, so 156px of the panel was empty. That did remove the 156px. It
also pinned the transcript at 160px across every width from 1024 to 2560, and moved the
dead space out of the panel and onto the page, where it grew from 343px under the composer
at 1024 to 983px at 2560. Two checks in `tests/browser.test.mjs` ("the message thread grows
with the window instead of capping at a fixed height" and "there is no growing strip of
dead window under the composer") failed on exactly that, and they are right: an empty panel
that grows with the window is what a transcript looks like, and a gate that stops halfway
down a large screen is not. The row is `1fr` again, with `height: 100%` back on `#messages`
because `align-items: start` otherwise leaves the box short inside its own track.

## 3. One gap, at every width

The margin reset that gave the phone a single rhythm lived inside `@media (max-width: 699px)`,
so every wider screen still carried whatever margin each child brought from a layout it no
longer has: `details.disc` 10 below, `details.disc.compact` 14 above, `button.danger` 20
above. Those stack on top of the container's `gap` rather than replacing it. Measured
distances between consecutive blocks: 10 / 10 / 10 / 24 / 34 / 40px at 768x1024, and
14 / 28 / 38px at 1440x900. Six blocks, four different gaps, none of them chosen. The reset
is now unscoped.

## 4. A short phone is a different problem from a narrow one

The phone block was measured and tuned at 390x844 and holds there: the composer's bottom
edge lands at y=754 against a fold of 811. At 360x640 the same rules put it at y=740 against
a fold of 607, so Send and Attach were 133px below the screen with the page at rest and the
person had to scroll to reach the button they came for. Nothing about the width caused it.
The window is 204px shorter and the layout spends a fixed number of pixels above the
composer regardless.

`@media (max-width: 699px) and (max-height: 700px)` gives the height back, cheapest first:
the folded capability note is 98px of a 278px composer and is the one block on the screen
that is pure explanation, so it goes (a fold nobody has opened yet, not information that was
on screen); the textarea drops to two lines; the transcript cap comes down with the window.
700px rather than 640, because at 700 the same arithmetic leaves about 40px of headroom, and
headroom smaller than the amount the verification box moves by when its two words wrap is
not headroom.

## 5. Tap targets and a one-pixel scrollbar

At 390x844: `#secret-toggle` 16x16, `label.toggle` 61.3x20.9, Save 55.5x34.1. The two that
matter are the ones used during a transfer. `.toggle` gets `min-height: 44px` on the label
rather than on the checkbox, because the label is already the hit area and a 44px checkbox
next to a 14px word looks wrong. File-row buttons go from 6px to 11px of vertical padding,
which reaches 44 without changing the type size.

At 360x640 the page had 1px of horizontal overflow, attributed to `a.foot-gh` overhanging by
1.4px: `.foot` is a six-item flex row with no wrap. It wraps now.

## 6. The sender could not see what they sent

Asked for verbatim: "Sender should also be able to see what they sent like a preview". The
sender's row was a name, a size and the word "Sent.", so the one person who could confirm
the right file went out was the only person who could not see it.

It costs no transfer. `File` extends `Blob`, so the same `decorateFileRow` that renders a
received image renders the local one. The ordering is the whole difficulty: `link.js`
releases `out.file` one line before it emits `file-sent`, and that event carries neither the
mime type nor the bytes, so a preview built in its handler would have nothing to work from.
`sendFilesNow` is the last place holding the real `File`, and it holds it for the whole
batch, so the preview is attached there. `Session.sendFile` now returns the transfer id
(it returned `undefined`, and the id existed only inside it) so the caller can find the row.

The VirusTotal caution is suppressed on a sent row, and that is a statement about provenance
rather than a rendering flag: telling somebody to upload their own outgoing file to a third
party that publishes it would be advice to leak the thing they just chose to send privately,
which is the exact harm the caution's own wording warns about. Until now the rule was
enforced by the caller, because `finishFileRow` returned at "Sent." and there was no route
into `preview.js` at all. There is one now, so it is enforced where it is stated.

## 7. A backgrounded tab killed its own transfer

Reported as "no send unless the screen is on". Two separate defects, one of them the
reported cause and one of them not.

**The measured cause: a resume that was refused for being correct.** Five instrumented
two-peer runs settled it. A hidden tab does NOT stop sending: timers clamp from 250ms to
1000ms, `Date.now()` stays real, and the send completes. What kills it is the recovery. When
the sending page is genuinely frozen, the bytes already sitting in its SCTP buffer go on
being delivered, and the receiver's sink advances while the sender cannot count it. The
receiver asks to continue from where it was, the answer echoes that same offset a round trip
later, and by then the sink is further on: measured 4,439,040 bytes further in one run and
3,394,560 in another, which is the buffer draining. `judgeResumeResponse` compared the two
with `offset !== at` and answered `bad_offset`, which fails the transfer on both sides with
no retry.

Behind is now accepted and corrected forward to what this side actually holds. The re-sent
chunks are dropped by index in `createIndexedSink`, so the cost is bandwidth, not
correctness. Ahead is still refused: an offset past the contiguous frontier would splice a
hole that no length check on either side can see. Negative is refused with it. The
regression test is in `tests/download.test.mjs` and was run against the strict-equality code
first, where the behind case fails and the other two pass.

**The other one, which the experiment refuted as the cause but did not exonerate.** The
drain deadline in `peer.js` was wall clock: `Date.now() + 30_000`, with no guard of the kind
`link.js` gives its two auth timers. A frozen page thaws with the deadline already behind
it, so the first poll rejects with "the other device stopped accepting data" about a peer
that did nothing. The experiment never reached it, because on a loopback link the longest
pause was about 7 seconds, but a slow link and a locked phone are not a loopback link.

It measures running time now: a poll that arrives later than its interval hands the
overshoot back. A page that is merely hidden still times out, because a clamped poll
overshoots by a bounded amount each round, so the stretch is roughly four times rather than
unbounded. `tests/drain.test.mjs` covers all three cases (running, frozen, throttled) and
was run against the wall-clock version first, where the two freeze checks fail.

`navigator.wakeLock` stays unused. It is released on hide by definition, so it addresses a
sleeping screen and not a switched app, and neither of the two defects above was about the
screen.

## 8. The wordlist stopped being a boot cost

`words.js` is 61 KB raw, roughly 30 KB gzipped, and was a fifth of the gate's eager module
graph. It was there because `crypto.js` imported `decodeGateCode` and re-exported eleven
symbols, so it arrived before the page could decide whether the person was creating a gate,
joining one, or reading the screen.

It is behind `loadGateCode()` in `crypto.js` now, one shared promise, cleared on failure so
a bad fetch is not remembered as the answer. Three callers await it: `startCreate` before
minting a code, `startJoin` before decoding one, and `deriveSecret`, which was already
async. `afterAgreement()` skips it entirely when there is neither a link fragment nor a
secret held for the tab, which is every first visit.

The accessor stays in `crypto.js` rather than each caller importing `words.js` directly, so
the rule that everything about a gate code arrives from one module survives the split.
Two test files that were reaching the wordlist THROUGH `crypto.js` now import it directly,
which is also the honest import: they are testing the list.

The 2026-08-10 note in `tests/size.test.mjs` said this was not excludable, on the grounds
that a lazy import behind Create moves the same fetch behind the primary action instead of
removing it. That was answered rather than overruled: it removes the fetch for everyone who
presses neither button, and for those who do it overlaps a network round trip they were
going to wait for anyway. What it must not do is delay the join path, which is why the
fetch starts before `decodeGateCode` rather than inside its error handler.

This is also what paid for the rest of this document. The eager graph was 2,128 B over its
raw ceiling with the status and preview work in it, and the ceiling's own comment forbids
raising it to make room for a feature. Nothing was raised.

## 9. The drawers move like drawers

Connection details and Games are the only disclosures on this site that get opened and shut
over and over, and they were still half animated: a 150ms 4px fade in, and nothing at all on
the way out. In the rail, where they now live for the length of a gate, that read as a snap.

They unfold from the summary's edge over 300ms instead, and they animate closed over 150ms,
which is the one place on this site that does. A `<details>` shuts between two frames, so
`app.js` preventDefaults the summary click, marks the panel and lets `wg-fold` run before
setting `open = false`, with a 500ms timer as the backstop: `animationend` does not fire for
a `display: none` element, and a drawer that could be opened and never closed would be worse
than the snap this replaces. Under `prefers-reduced-motion` the interception does not happen
at all, so the close is native and instant. Onboarding's five panels are untouched: they are
read once on the way in, and a panel somebody has decided to be rid of should be gone.

The fold is `scaleY` and `opacity`, and the panel's HEIGHT still changes in a single frame.
That is the deliberate half. Animating height would relayout the whole connected screen on
every frame of every open, over a live transfer and a running board, which is what the
motion budget in `tests/motion.test.mjs` refuses. A third travel token, `--fold-scale`, was
added rather than hard-coding 0.94, because the reduced-motion branch collapses every
translate and every scale in the file from one place and a literal would have been the one
piece of travel it could not reach.

An arriving invitation gets the same 4px rise a message landing in the transcript gets, once
per invitation: `gameui.js` sets the class where it decides an invitation is new, and
`renderInvite` consumes it, so a re-render for an unrelated notice does not replay it.
Motion that repeats without a new event stops meaning "something happened".
